# 로또

## 과제 개요

해당 과제는 6자리의 로또 번호와 사용자가 입력한 6자리의 숫자와 1자리의 보너스 숫자로 결과를 구하는 로또 게임을 구현하는 과제이다.<br>
해당 과제의 주요 구현 목표는 클래스를 통해 로또 관련 필드를 정의하고 생성된 객체들을 통해 하나의 큰 기능을 수행하도록 구현하는 것이다.<br>
추가적으로 로또 클래스의 각 기능을 구현하면서 함수에 대한 단위 테스트 함수로 구현한 기능을 검증하는 영역을 확보해야 한다.

## 기능 흐름 정리

1. 로또 구입 금액을 입력한다.(로또 한장당 가격은 1000원)
2. 구입 금액에 따른 로또 개수를 구한다.
3. 로또의 개수만큼 사용자의 추첨 번호를 생성한다.(쉼표 기준 6자리의 중복이 없는 1~45 숫자)
4. 사용자의 추첨 번호를 입력받는다. ( 기준 동일 )
5. 사용자의 보너스 추첨 번호를 입력한다. (추첨 번호와 중복되지 않는 1개의 숫자)
6. 생성된 로또번호와 사용자의 번호를 비교해서 각 로또의 결과를 도출하고 결과 통계를 낸다.
    - 1등: 6개 번호 일치 / 2,000,000,000원
    - 2등: 5개 번호 + 보너스 번호 일치 / 30,000,000원
    - 3등: 5개 번호 일치 / 1,500,000원
    - 4등: 4개 번호 일치 / 50,000원
    - 5등: 3개 번호 일치 / 5,000원
7. 당첨 등수에 따라서 몇개가 당첨됐는지 출력한다.
8. 구입 금액과 당첨 금액의 비율을 통해 수익률을 출력한다.

## 기능 요구사항 체크리스트

입력

-   [x] `구입금액을 입력해 주세요.` 출력과 함께 사용자가 로또 구입 금액을 입력한다.
-   [x] `당첨 번호를 입력해 주세요.` 출력과 함께 사용자가 추첨 번호를 입력한다.
-   [x] `보너스 번호를 입력해 주세요.` 출력과 함께 사용자가 보너스 추첨 번호를 입력한다.

입력 처리

-   [x] 입력된 로또 구입 금액을 숫자로 바꾸어 `1000원` 단위로 나누어 구입 로또 개수를 구한다.
-   [x] 사용자 추첨 번호를 `,` 쉼표를 기준으로 구분하여 숫자로 저장한다.
-   [x] 보너스 번호를 숫자로 변환한다.

로또 게임

-   [x] 로또 번호 생성 : 6자리의 중복이 없는 1에서 45 사이의 난수를 생성한다.
-   [x] 구입 로또 생성 : 구입 개수만큼 ‘로또 번호 생성’ 한다.

-   [x] 로또 당첨 확인 : 추첨번호와 로또를 비교하여, 일치하는 번호의 개수를 구한다.
-   [x] 보너스 번호 확인 : 로또에 보너스 번호가 있는지 확인한다.
-   [x] 당첨 등수 확인 : 추첨 번호 일치 개수와 보너스 번호 일치 여부를 통해 당첨 등수를 구한다.

-   [x] 구입 로또 결과 확인 : 구입한 로또들의 ‘로또 당첨 확인’ 과 ‘보너스 번호 확인’으로 각 로또들의 ‘당첨 등수 확인’한 결과를 도출한다.
-   [x] 로또 수익률 계산 : 각 로또의 당첨 등수에 따른 상금을 모두 합하여 구입금액과 비교한 수익률을 구한다.(소수점 둘째 자리에서 반올림)

출력

-   [x] 사용자가 구입한 로또의 개수를 `[개수]개를 구매했습니다.` 로 출력한다.
-   [x] 사용자가 구입한 모든 로또의 결과를 `[a, b, c, d, e, f]` 와 같은 형식으로 한줄씩 출력한다.
-   [x] 당첨 통계 추출의 헤더를 `당첨 통계\n---` 와 같은 형식으로 출력한다.
-   [x] 사용자가 구입한 로또의 결과에 따른 각 당첨 등수를 각 등수의 형식에 따라 출력한다.
    -   `3개 일치 (5,000원) - n개`
    -   `4개 일치 (50,000원) - n개`
    -   `5개 일치 (1,500,000원) - n개`
    -   `5개 일치, 보너스 볼 일치 (30,000,000원) - n개`
    -   `6개 일치 (2,000,000,000원) - n개`
-   [x] 총 수익률을 `총 수익률은 nn.n%입니다.` 와 같은 형식으로 출력한다.

## 구현 중 주요 고려사항

### TDD 개발 방법론 적용

TDD(Test Driven Development) 개발 방법론을 적용해봤다.<br>
TDD 개발 방법론이란 기능 단위 테스트를 작성하고 테스트에 대한 코드를 작성한 뒤 코드를 개선하며 단위테스트를 반복하는 개발 방법론이다.<br>
TDD의 장점은 다음과 같다<br>

1. 디버깅이 간편해짐 : 기능별로 단위 테스트를 미리 작성하고 자동화된 테스트를 진행하여 어느 기능에서 장애가 발생했는지 빠르게 인지할 수 있다.
2. 재설계의 시간을 단축 : 코드를 작성하기 전 미리 단위 테스트를 생각해보기 때문에 다양한 예외 사항에 대해 생각해볼 수 있다.

구현하는 과정에서 초기엔 TDD의 기본 구현 절차인 RED(단위 기능 테스트 작성)-GREEN(단위 기능 구현)-BLUE(리펙토링) 단계를 거치면서 순조롭게 구현을 진행했다.<br>
TDD 방법론을 사용한 뒤에 개발사이클이 정해져 가는 느낌이 들어 개발과 디버깅 및 테스팅 프로세스가 자연스러워졌다. 특히 리팩토링 뒤 내가 구현하고자했던 단위 기능이 여전히 동작하는지 곧 바로 신속하게 파악이 가능하다는 점이 마음에 들었다.<br>
하지만 기능 단위의 기준애서 벗어나 더 큰 역할을 하는 기능에 대한 테스트를 잘못 생각하기 시작하면 테스트 코드를 작성하는 단계의 시간이 길어지는 문제가 발생할 뿐만 아니라 기능을 구현하더라도 리팩토링 과정이 복잡해지게 되어, 기존의 구현 단계보다 약 2배 더 소요되는 문제점이 있었다.<br>
커뮤니티에서 받은 의견으로도 리팩토링의 수준을 낮춰보라는 의견이 있었기에 이 점을 유의하면서 구현을 이어갔다.

### 캡슐화 및 유의미한 이름을 고려하며 구현하기

2주차의 공통 피드백에서도 나왔듯이 함수는 하나의 기능만을 수행하도록 구현하는 것이 바람직하고 모듈 하나하나의 의미가 확실해지도록 구현되도록 유의하면서 과제를 진행했다.<br>
지난 과제의 코드리뷰를 하면서 다른 분들의 코드에서 에러 클래스를 상속하여 에러를 유의미하게 던져 세부적인 에러 처리를 유도하는 것을 확인했다. <br>
이러한 방식을 보고 세세한 부분까지 유의미하게 만드는 것이 더욱 유연한 코드를 만들면서 가독성이 좋고 리팩토링이 수월해지는 코드의 기반이 되는 것이라는 생각이 들었다.<br>
이러한 생각은 이번 과제를 진행하면서 확실해졌다. 구현 과정에서 함수를 자르고 선언적으로 코드를 작성할수록 수정해야할 코드의 위치나 문제의 원인이 되는 코드를 빠르게 유추가 가능케되었기 때문이다.<br>

## 구현 내용

### 폴더 구조

```
src
├── App.js // 컨트롤러
├── application // 컨트롤러 관련 기능
│   ├── InputHandler.js // 사용자 입력의 처리 과정을 정의
│   ├── InputValidator.js // 사용자 입력의 형식에 대한 유효성 검사
│   └── OutputHandler.js // 결과 출력
├── constants // 상수값
│   ├── GameConfig.js // 로또의 세팅값
│   ├── Reg.js // 정규표현식
│   └── message // 각종 메세지
│       ├── Error.js
│       ├── Input.js
│       └── Output.js
├── error // 에러 클래스
│   └── ValidationErrors.js
├── index.js
├── lottoGame // 도메인
│   ├── LottoGame.js // 로또 게임 클래스
│   ├── gameUtils // 로또 게임 관련 유틸 함수
│   │   ├── CalculateLottosStatistics.js // 구임한 개별 로또의 결과
│   │   └── CalculateProfitRatio.js // 구입한 총 로또의 수익률
│   └── lotto
│       ├── AutoLotto.js // 구입한 로또
│       ├── Lotto.js
│       └── UserLotto.js // 사용자의 추첨 로또
├── utils
│   ├── Common.js
│   └── InputProcess.js // 사용자 입력의 전처리 관련 유틸 함수
└── view // 입력과 출력 담당
    ├── inputView.js
    └── outputView.js
```

주요 폴더는 application, lottoGame, view로 모듈간 의존도를 줄이려고 노력하면서 구현을 진행하였다. 가져와서 사용하는 측은 가져오는 기능의 내부 로직을 몰라야 한다는 점을 유의하면서 구현했다.

구현 마지막에 로또의 숫자와 보너스 번호 입력값에 대한 규칙 조건 유효성 검사에서 에러 처리를 통해 오류가 있는 입력을 재입력 받는 로직을 구현하지 못한 것이 아쉬웠다.<br>
예를들어 숫자가 1,,4 와 같은 형식의 문제는 입력 처리과정에서 재입력을 즉각적으로 받도록 구현했다. 그런데 1,46과 같은 로또 규칙의 문제는 LottoGame 내부에서 유효성 검사를 진행했다. 바로 이 부분에서 효과적으로 에러처리를 할 수 있는 방안이 모호하여 프로젝트에 적용하지 못하였다.<br>
처음 생각한 것은 App.js 파일 내부에서 에러 처리를 하는 것이었다. 하지만 여기에서 에러 처리를 실시하면 App의 컨트롤러 및 오케스트레이션 이라는 책임에 에러 처리라는 책임이 추가되어 좋지 않은 리팩토링 방향이었다.<br>
그렇다고 개별적인 로또 클래스 안에서 처리하는 것도 동일한 책임을 추가하는 것이기에 다른 아이디어가 필요했다.<br>
따로 모듈로 분류하여 관리하는 것이 최선의 방법이지만 현재 폴더 구조에서 어느 부분에 추가해야하는지에 대한 문제로 이어졌다. 해당 고민 과정의 시점이 마감 기한에 가까웠던지라 리팩토링을 본격적으로 진행하지 못하였지만, 다음 과제에선 이번 과제의 목표였던 TDD와 캡슐화의 과정을 체득하였으니 에러를 처리하는 리팩토링 방법을 고민해볼 예정이다.

## 추가적으로 생각할점

-   에러 처리의 효율적인 방안
-   서비스 계층을 생각해보기
-   MVC 패턴의 본질을 다시 한번 생각해보고 다른 아키텍쳐 패턴 고려해보기
    -   이 부분은 커뮤니티에서 다른 챌린저의 블로그 글을 참고한 것에 비롯되었다. 물론 지금까지 과제를 진행하면서 MVC 패턴을 의미없이 적용하지 않았다. 그동안의 구현과정을 보면 처음부터 MVC 패턴을 고려하지 않고 리팩토링 과정에서 자연스럽게 MVC 패턴과 유사하게 형성되었기 때문이다. 하지만 해당 블로그의 글에서 이번 과제어서 사용되는 MVC 패턴의 몇가지 오류를 짚어줬는데, 아키텍쳐 패턴에 대한 상당한 인사이트를 받을 수 있었다. 따라서 다음 과제에선 리팩토링 방법론을 통해 여러가지 방안을 시도해볼 것이다.
